## Что работает правильно по коду и живой схеме

Цены заказа берутся backend из products, не из клиентской суммы. Подтверждение ограничено сроком действия и совпадением телефона. Live finalize_verified_checkout блокирует checkout и verification FOR UPDATE, создаёт клиента/заказ/позиции и вызывает reserve_web_order_items в одной транзакции; ORDER_CREATED возвращает duplicate. Остатки неизвестного товара консервативно закрыты. Source подтверждает серверный reserve с блокировкой availability state/item. Применение/проверка выбранного Telegram контакта выполняется ботом.

SSE poll имеет busy guard и не обращается к БД без подключённых клиентов. Интервал config 60с имеет busy guard, timeout 10с и skip hidden; спрос обновляется при открытой корзине с abort/sequence guard. Roulette таймеры локальные, не создают API loop. Защита платежей на сайте не оценивалась как эквайринг: сайт оформляет заказ, не выполняет карточную оплату.

## Схема и масштаб

Supabase performance advisors: 5 INFO unindexed_foreign_keys (checkout_sessions.order_id, loyalty_ledger.order_id/program_id, order_items.order_id/product_id), 9 INFO unused_index. Не удалять unused индексы автоматически: малая история нагрузки не доказывает ненужность. Индекс checkout verification token отсутствует; orders status+created_at отсутствует. Метаданные pg_class дают оценки лишь десятков записей (не точные counts), поэтому текущая маленькая БД не доказывает устойчивость на большом объёме.

Рекомендации advisor: https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys ; https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index .
